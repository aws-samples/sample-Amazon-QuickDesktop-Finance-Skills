# 社保公积金基数核定

## Overview
在社保公积金申报前，校验每名员工的缴费基数是否落在合规区间（社平工资 60%~300%）、基数是否等于工资的托底封顶值、以及单位/个人缴费额是否等于基数×费率。核心验收判据是**基数白名单 + 缴费恒等式**，识别超限基数、托底封顶错误、缴费额计算错误。

## 数据敏感性
薪酬含员工 PII。**执行前先加载 `financial-local-safety` skill**，本地模式处理。运行时模型只做编排、不接触原始薪酬数据，只看结果摘要；核定校验在本地沙箱由确定性脚本完成。

## 上层判据（不折旧 · 跨平台）
| 判据 | 规则 | 触发 |
|------|------|------|
| **基数白名单** ⭐ | 下限(社平60%) ≤ 基数 ≤ 上限(社平300%)；社保上下限由脚本按社平工资×60%/×300% 推导，`params.csv` 中的社保上下限只比对，不一致记「社保基数下限≠社平工资×60%」「社保基数上限≠社平工资×300%」（`param_issues`，计入 `all_ok`） | 越界 → fail |
| **缴费恒等式** ⭐ | 单位/个人缴费 == 基数 × 费率 | 不等 → fail |
| **托底封顶** | 基数 == clip(月工资, 下限, 上限) | 不等 → fail/review |
| **完整性** | 每人各险种齐全 | 缺 → 漏缴 |

- **Mode**: `deterministic`

- **Input**: 无

### Step 3: 执行基数核定
- **Mode**: `deterministic`
- **Tool**: `run_python_on_device`（计算只在设备端进行，见 financial-local-safety 铁律 2）

- **Output**: 逐人核定 + 缴费汇总 + 实缴vs应缴差异
- **Validate**: 守恒自检 assert；异常逐人列出

### Step 5: 归档
- **Mode**: `deterministic`

- 缴费汇总：基数合计、单位/个人缴费、实缴vs应缴差异

## Lessons Learned
### Do
- 基数超上下限必须托底/封顶——低于下限按下限缴、高于上限按上限缴。
- 缴费额由基数×费率精确计算，白名单管基数、恒等式管缴费额。
- 社平工资、费率、上下限按参保地政策年度参数化更新。

### Don't
- 不要按实际工资缴（超限时）——必须托底封顶。
- 不要手工估填缴费额——回归基数×费率。

### Common Failures
- 多险种字段多：脚本示例以养老为主，可扩展医疗/失业/公积金各栏同理校验。
- 社平工资口径（全口径/非私营）不同导致上下限差异：参数化确认。
- 中文表头 BOM：用 `encoding="utf-8-sig"`。

### When to Ask the User
- 参保地社平工资、各险种费率、基数上下限比例（部分地区非60%/300%）确认。
- 是否需扩展到医疗、失业、工伤、生育、公积金全部险种核算。

## 判据
| 判据 | 规则 | 结果 |
|------|------|------|
| 基数核定 ⭐ | 社保基数=clamp(核定工资,社平60%,社平300%)；公积金=clamp(核定工资,最低工资,封顶)；新入职按首月工资 | 不符 |
| 基数区间 | 下限 ≤ 基数 ≤ 上限（社保、公积金各自区间） | 越界 |
| 同员工社保基数一致 | 养老/医疗/失业/工伤四险基数相同 | 待核实 |
| 费率白名单 | 单位/个人费率 == 规则表 | 不符 |
| 缴费恒等式 ⭐ | 单位缴费=基数×单位费率；个人缴费=基数×个人费率 | 不符 |
| 完整性 | 每人每险种齐全；缴费记录员工必须在花名册 | 漏缴 / 花名册外 |
| 守恒 | 实缴 vs 应缴（核定基数×规则费率），分单位/个人 | 自检 |

## 样本数据（演示 · 全部虚构）
示例集团（虚构）30 名员工 × 5 险种（养老/医疗/失业/工伤/公积金）= 150 条；社平 8000、社保基数区间 [4800, 24000]、公积金封顶 36549、含新入职。
- `samples/clean/`：150 条全部正确，实缴 = 应缴 33.4 万
- `samples/error/`：植入 12 处（基数低于下限、高收入未封顶、基数低报、各险种基数不一致、单位/个人缴费算错、费率用旧 14%、漏缴医疗、新入职按下限、公积金超封顶、花名册外人员、缴费基数写成千分位无法解析），11 处触发 22 条不符、1 处登记为数据质量问题，全部命中、无误报；实缴比应缴少 5,076.65


## 自检 vs 正式运行（边界 · 必读）

本 skill 捆绑了 `samples/` 夹具与 `self_check.py`，**仅用于验证脚本本身是否健康，绝不参与正式业务运行**。两者必须严格分开：

| | 正式运行 | 自检（回归测试） |
|---|---|---|
| 输入 | **用户当期数据**，路径由调用者显式提供 | 内置 `samples/{clean,error}/` 夹具 |
| 入口 | `check(缴费基数目录)` | `python scripts/self_check.py` |
| 目的 | 核对这套业务数据 | 验证脚本行为与黄金答案一致 |
| 何时跑 | 每次业务核对 | 脚本改动后 / 定期体检 |

**铁律**：
- 校验函数**不设指向 samples 的默认路径**——数据路径必填，调用者给什么就核什么，绝不会在漏传时静默去核样本、假报"全部通过"。
- `samples/` 是隔离夹具（体检用），不是"默认数据集"，正式运行永不读它。
- 自检是独立命令（`self_check.py`），和业务运行不共用入口。

> **自检怎么用**：`python scripts/self_check.py` → 对 `samples/clean/` 应全部通过（全平），对 `samples/error/` 应低于 100% 并正好抓出植入的错误，与 `samples/expected.json` 黄金答案逐项比对；一致则退出码 0（脚本健康），不一致则非 0（脚本可能已退化）。植错版是最强验证器——有确定的已知错误数与期望值，脚本一旦退化立刻暴露。

## 判据覆盖声明与已知盲区

> 本场景判据可捕获：**恒等式、白名单、交叉一致** 类错误。但每类自动校验都有其数学上的固有盲区——以下显式列出「判据抓不到什么」及对应处置。**「知道自己抓不到什么」比「能抓到什么」更是可信交付的证明。**

### 已知盲区（判据抓不到的错误类型）

| 盲区 | 关联判据 | 判据为何抓不到 | 处置 | 可闭合性 |
|------|:--:|------|------|:--:|
| 合法但不适用 | 白名单 | 值在白名单内但用错场景（如6%与13%都合法，用错税率照样过） | 单字段白名单→交叉白名单（业务类型×允许值）；白名单版本化+生效日 | 🟢可自补 |
| 口径与时点 | 恒等式 | 等式内部自洽，但取数口径（时点/主体/准则）错，等式照样成立 | 口径三元组声明（时点+主体+准则）；跨期衔接校验（本期期初=上期期末） | 🟢可自补 |
| **在职vs参保范围盲区** ⚠️ | 场景特有 | 未参保员工不在参保表中，社保基数判据对其永远全绿 | 在职名册 vs 参保名册双向比对（在职未参保/参保非在职） | 🟢可自补 |

> **已接入** `scripts/social_insurance_check_v2.py`：五险一金逐险种基数核定与区间、同员工社保基数一致、费率白名单、缴费恒等式、漏缴与花名册外、实缴vs应缴分向守恒。

### 可闭合性三档
- 🟢 **可自补**：加一段确定性检查即可闭合，零外部依赖——应直接实现。
- 🟡 **需外部锚点**：缺的是「第二个独立源」而非代码，须接入权威源（工商股权/银行/金税/合同）后方能校验——对客户标注为「需接入 X 源」。
- 🔴 **不可闭合**：结构上无验证基准（如员工自报项、需实物确认项），只能显式声明并交人工。

### 通用盲区补丁位（据本场景判据勾选）
- ☑ **范围完备性**：双向名单比对（A有B无 / B有A无 分别列示）——防「未进检查范围」的记录永远全绿
- ☑ **笔数守恒**：金额守恒之外加笔数守恒——抓成对反向错误
- ☑ **分向列示+分向限额**：正/负、双向单边分别设限——防净额掩盖
- ☑ **交叉白名单**：业务类型×允许值，白名单版本化+生效日——防「合法但不适用」
- ☑ **口径三元组**：时点+主体+准则声明 + 跨期衔接（本期期初=上期期末）——防口径错
- ☐ **归一化+模糊指纹**：去空格/全半角/前导零 + 组合键指纹——防唯一性绕过
- ☐ **外部锚点**：关键项引第三方独立源交叉验证——防同源错误
