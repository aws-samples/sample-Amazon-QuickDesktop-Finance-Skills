# 收款核销匹配

## Overview
将客户收款单与应收发票做核销匹配——确认每笔收款销的是哪些发票、每张发票收到多少款，识别孤立收款、部分核销、一对多核销、金额不符。核心验收判据是**交叉一致 + 核销守恒 + 应收闭环**：三方核销金额相等、期初应收减核销等于期末应收，锁死账实一致。

## 数据敏感性
收款含客户 PII 与银行信息。**执行前先加载 `financial-local-safety` skill**，本地模式处理。

## 上层判据（不折旧 · 跨平台）
| 判据 | 规则 | 触发 |
|------|------|------|
| **交叉一致** ⭐ | 收款金额 == 该收款的Σ核销金额 | 不等 → difference/exception |
| **核销守恒** ⭐ | Σ核销 == Σ发票已核销 == Σ收款已核销 | 不等 → 核销数据错误 |
| **应收闭环** | 期初应收 − 核销 == 期末应收 | 不等 → 账实不符 |
| **完整性** | 每笔收款须有核销关系 | 无 → 孤立收款 exception |
| **守恒（自检）** | Σ状态数 == 总数 | 不等 → 分析错误 |

## Lessons Learned
### Do
- 双向校验：既查收款单核销是否完整，也查发票收款是否到位。
- 用核销守恒（三方金额相等）+ 应收闭环（期初−核销=期末）两道 assert 锁死账实。
- 部分核销是正常分期回款，判 partial 并跟踪剩余应收，不判异常。

### Don't
- 不要对孤立收款强行匹配发票——判 exception 交人工核实。
- 不要只做单向（只看发票或只看收款）——单方核销会被守恒暴露。

### Common Failures
- 核销守恒 assert 失败：核销关系引用了不存在的发票号/收款单号（外键断裂），先校验引用完整性。
- 无独立核销关系表：需从收款单的核销明细字段拆解，或按客户+金额推断（需用户确认口径）。
- 中文表头 BOM：用 `encoding="utf-8-sig"`。

### When to Ask the User
- 核销关系来源（独立表 / 收款单内嵌明细 / 需推断）确认后再定读取方式。
- 部分核销的剩余应收是否结转下期、金额不符的处理口径按客户规则确认。

## 判据
| 判据 | 规则 | 结果 |
|------|------|------|
| 收款 ↔ 银行 ⭐ | 每张收款单对应一笔银行到账；金额相等；收款日期不早于到账、滞后 ≤3 天；银行到账无收款单 → 到账未入账 | 不符 |
| 付款人归属 ⭐ | 银行付款账户 ∈ 该客户的付款账户白名单 | 收款挂错客户 |
| 核销准入 | 收款单、发票存在；发票未作废；收款客户 == 发票客户；同一(收款,发票)只核销一次 | 无效核销（不冲减应收） |
| 边界 | Σ核销 ≤ 收款金额；Σ核销 ≤ 发票应收 | 超收款 / 超额核销 |
| 守恒 | Σ有效核销 == Σ发票已核销 == Σ收款已核销；收款 == 核销 + 未核销余额 | 自检 |
| 应收闭环 | 正常发票应收 − 有效核销 == 期末应收，对 1122；未核销收款对 2203 | 不符 |

## 自检 vs 正式运行（边界 · 必读）

本 skill 捆绑了 `samples/` 夹具与 `self_check.py`，**仅用于验证脚本本身是否健康，绝不参与正式业务运行**。两者必须严格分开：

| | 正式运行 | 自检（回归测试） |
|---|---|---|
| 输入 | **用户当期数据**，路径由调用者显式提供 | 内置 `samples/{clean,error}/` 夹具 |
| 入口 | `check(发票+收款+银行目录)` | `python scripts/self_check.py` |
| 目的 | 核对这套业务数据 | 验证脚本行为与黄金答案一致 |
| 何时跑 | 每次业务核对 | 脚本改动后 / 定期体检 |

**铁律**：
- 校验函数**不设指向 samples 的默认路径**——数据路径必填，调用者给什么就核什么，绝不会在漏传时静默去核样本、假报"全部通过"。
- `samples/` 是隔离夹具（体检用），不是"默认数据集"，正式运行永不读它。
- 自检是独立命令（`self_check.py`），和业务运行不共用入口。

> **自检怎么用**：`python scripts/self_check.py` → 对 `samples/clean/` 应全部通过（全平），对 `samples/error/` 应低于 100% 并正好抓出植入的错误，与 `samples/expected.json` 黄金答案逐项比对；一致则退出码 0（脚本健康），不一致则非 0（脚本可能已退化）。植错版是最强验证器——有确定的已知错误数与期望值，脚本一旦退化立刻暴露。

## 判据覆盖声明与已知盲区

> 本场景判据可捕获：**守恒、白名单、交叉一致、唯一性** 类错误。但每类自动校验都有其数学上的固有盲区——以下显式列出「判据抓不到什么」及对应处置。**「知道自己抓不到什么」比「能抓到什么」更是可信交付的证明。**

### 已知盲区（判据抓不到的错误类型）

| 盲区 | 关联判据 | 判据为何抓不到 | 处置 | 可闭合性 |
|------|:--:|------|------|:--:|
| 净额掩盖 | 守恒 | 正负成对错误相互抵消，净差为0但双向各错（如银行多记100+企业多记100） | 分向列示+分向限额；加「笔数守恒」配合金额守恒 | 🟢可自补 |
| **发票级唯一性缺失** ⚠️ | 场景特有 | 金额相同的两张发票互换核销，三方守恒仍成立 | 发票级唯一匹配，不能只靠金额守恒 | 🟢可自补 |

> **已接入** `scripts/ar_settlement_v2.py`：以银行到账为外部锚点核对收款（金额、日期、到账未入账；银行流水号或发票号重复时报出，不用后一行覆盖前一行），付款账户白名单识别挂错客户，核销准入（存在、未作废、同客户、不重复），核销三方守恒、收款守恒、应收与预收分别对总账。

### 可闭合性三档
- 🟢 **可自补**：加一段确定性检查即可闭合，零外部依赖——应直接实现。
- 🟡 **需外部锚点**：缺的是「第二个独立源」而非代码，须接入权威源（工商股权/银行/金税/合同）后方能校验——对客户标注为「需接入 X 源」。
- 🔴 **不可闭合**：结构上无验证基准（如员工自报项、需实物确认项），只能显式声明并交人工。

### 通用盲区补丁位（据本场景判据勾选）
- ☑ **范围完备性**：双向名单比对（A有B无 / B有A无 分别列示）——防「未进检查范围」的记录永远全绿
- ☑ **笔数守恒**：金额守恒之外加笔数守恒——抓成对反向错误
- ☐ **分向列示+分向限额**：正/负、双向单边分别设限——防净额掩盖
- ☑ **交叉白名单**：业务类型×允许值，白名单版本化+生效日——防「合法但不适用」
- ☑ **口径三元组**：时点+主体+准则声明 + 跨期衔接（本期期初=上期期末）——防口径错
- ☑ **归一化+模糊指纹**：去空格/全半角/前导零 + 组合键指纹——防唯一性绕过
- ☑ **外部锚点**：关键项引第三方独立源交叉验证——防同源错误
