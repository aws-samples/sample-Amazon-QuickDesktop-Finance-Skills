# 关联方往来对账

## Overview
在合并报表前，对集团内关联方之间的往来交易做双向一致核对——同一笔关联交易，销售方记应收(+)、采购方记应付(−)，双方金额必须对称相等。核心验收判据是**交叉一致 + 抵消守恒**：A方金额=−B方金额，且全集团往来净额须为 0。识别金额不符、单边登记、方向错误、时间性差异，为合并抵消提供干净基础。

## 数据敏感性
集团内部往来属敏感数据。**执行前先加载 `financial-local-safety` skill**，本地模式处理。运行时模型只做编排、不接触原始往来数据，只看结果摘要；配对核对在本地沙箱由确定性脚本完成。

## 上层判据（不折旧 · 跨平台）
| 判据 | 规则 | 触发 |
|------|------|------|
| **交叉一致** ⭐ | A方金额 == −B方金额（双向对称）| 不等 → difference |
| **抵消守恒** ⭐ | Σ全体往来金额 == 0 | ≠0 → 单边/方向错误 |
| **完整性** | 每笔关联交易双方都入账，且只入一次 | 单边 / 重复入账 → exception |
| **对手方对称** | A 的对手方 = B 的记账实体，且反之 | 否 → exception |
| **类型一致** | 双方交易类型相同 | 否 → difference |
| **方向正确** | 一方应收(+)、一方应付(−) | 同向 → 方向错误 exception |
| **时间性** | 双方入账日期差 ≤ 阈值 | 超阈 → 时间性差异 |

## Workflow

### Step 1: 加载安全契约
- **Mode**: `deterministic`
- **Tool**: `load_skill`；随后按 financial-local-safety Step 1 用 `folder_list`、`list_outposts` 做前置校验
- **Input**: 无
- **Output**: 已加载 financial-local-safety

### Step 2: 读取关联往来台账
- **Mode**: `agentic`
- **Input**: `{{ledger_path}}`
- **Output**: 关联往来记录，按交易号归集
- **Validate**: 交易号、记账实体、对手方、金额字段齐全；同交易号应有双方两条
- **On failure**: 若各子公司台账分散，需先合并为一张全集团台账；符号口径（应收+/应付−）不一致时先标准化。

### Step 3: 执行双向核对与抵消守恒
- **Mode**: `deterministic`
- **Tool**: `run_python_on_device`（计算只在设备端进行，见 financial-local-safety 铁律 2）
- **Input**: `{{ledger_path}}` `{{marked_path}}` `{{registry_path}}` `{{balances_path}}`，调用 `scripts/intercompany_recon_v2.py` 的 `reconcile(ledger, marked, registry, balances)`
- **Output**: 逐交易对账结果 + 抵消差额（分向列示正差/负差/毛额）+ 各实体净额 + 单边记录配对提示 + 关联方清单完备性（未标记关联方及其余额）+ 输入指纹与时间戳
- **Validate**: 守恒自检 assert 通过；抵消差额(全体净额)理论应为0，≠0即列出不一致
- **On failure**: 若同交易号出现>2条，需先核对是否拆分入账或重号。

### Step 4: 生成讲解页/仪表盘（可选）
- **Mode**: `agentic`
- **Tool**: `run_python_on_device_with_write`（写入授权本地目录）
- **Input**: Step 3 的分析 JSON
- **Output**: 纯 SVG/CSS 自讲解 HTML（双向一致甜甜圈/差异类型条/实体净额双向条/待调整清单 + TTS 控制栏）
- **Validate**: 单屏不溢出、script 花括号配平、无 lookbehind 正则

### Step 5: 归档
- **Mode**: `deterministic`
- **Tool**: `file_copy`
- **Output**: 存入 `agent_files/artifacts/finance_scenarios/05_intercompany/`

## Lessons Learned
### Do
- 只有双向一致的往来才能进入合并抵消——差异和单边必须先调整。
- 抵消守恒（全集团往来净额=0）是硬校验，非0即存在未对称登记。
- 单边登记、方向错误判 exception 须人工调账，不可自动对冲。

### Don't
- 不要对单边/方向错误的往来强行抵消——会导致合并报表虚增虚减。
- 不要忽略符号方向——一方应收一方应付，同向即方向错误。

### Common Failures
- 同交易号出现超过2条：可能是拆分入账或交易号重复，需先归并核对。
- 各子公司符号口径不一（有的应付记正）：进脚本前先统一为应收+/应付−。
- 中文表头 BOM：用 `encoding="utf-8-sig"`。

### When to Ask the User
- 台账是否已汇总为全集团一张表、符号口径（应收/应付正负）确认。
- 时间性差异阈值（默认5天）、交易号匹配规则按集团财务口径确认。

## 样本数据（演示 · 全部虚构）
示例集团（虚构）6 家主体，2026-07 至 2026-09 共 120 笔关联交易、240 条对称分录，5 类业务（内部销售、内部服务、资金拆借、代垫费用、租赁）。
- `samples/clean/`：逐交易全部双向一致（120/120），抵消差额 0；但因 2 家未标记关联方，`all_ok=False`
- `samples/error/`：植入 18 处错误（金额不符 4 含一对 ±8000 互相抵消、单边 2、交易号不一致 2、方向错误 2、对手方不符 2、类型不一致 2、时间性 2、重复入账 1、金额写成千分位无法解析 1），全部命中、无误报
- 两版均附工商股权登记：示例联营公司F（联营 30%）、示例关联公司G（同一实际控制人）未被财务系统标记，往来余额合计 506.57 万未进入核对；该范围缺口计入 `all_ok`，因此两版均为 `all_ok=False`


## 自检 vs 正式运行（边界 · 必读）

本 skill 捆绑了 `samples/` 夹具与 `self_check.py`，**仅用于验证脚本本身是否健康，绝不参与正式业务运行**。两者必须严格分开：

| | 正式运行 | 自检（回归测试） |
|---|---|---|
| 输入 | **用户当期数据**，路径由调用者显式提供 | 内置 `samples/{clean,error}/` 夹具 |
| 入口 | `reconcile(往来台账, 关联标记, 工商登记, 对手方余额)` | `python scripts/self_check.py` |
| 目的 | 核对这套业务数据 | 验证脚本行为与黄金答案一致 |
| 何时跑 | 每次业务核对 | 脚本改动后 / 定期体检 |

**铁律**：
- 校验函数**不设指向 samples 的默认路径**——数据路径必填，调用者给什么就核什么，绝不会在漏传时静默去核样本、假报"全部通过"。
- `samples/` 是隔离夹具（体检用），不是"默认数据集"，正式运行永不读它。
- 自检是独立命令（`self_check.py`），和业务运行不共用入口。

> **自检怎么用**：`python scripts/self_check.py` → 对 `samples/clean/` 应逐交易 100% 双向一致（因 2 家未标记关联方 `all_ok=False`），对 `samples/error/` 应低于 100% 并正好抓出植入的错误，与 `samples/expected.json` 黄金答案逐项比对；一致则退出码 0（脚本健康），不一致则非 0（脚本可能已退化）。植错版是最强验证器——有确定的已知错误数与期望值，脚本一旦退化立刻暴露。

## 判据覆盖声明与已知盲区

> 本场景判据可捕获：**守恒、交叉一致、唯一性** 类错误。但每类自动校验都有其数学上的固有盲区——以下显式列出「判据抓不到什么」及对应处置。**「知道自己抓不到什么」比「能抓到什么」更是可信交付的证明。**

### 已知盲区（判据抓不到的错误类型）

| 盲区 | 关联判据 | 判据为何抓不到 | 处置 | 可闭合性 |
|------|:--:|------|------|:--:|
| 同源错误 | 交叉一致 | 两个「独立」来源实际同源，一起错则互证成功 | 标注每个来源的真实独立性；关键项引外部锚点（工商/银行/金税/合同） | 🟡需外部锚点 |
| 范围盲区 | 交叉一致 | 只核对「已进入两表」的记录，单边未登记项不进对比 | 双向名单比对：A有B无 / B有A无 分别列示 | 🟢可自补 |
| 净额掩盖 | 守恒 | 正负成对错误相互抵消，净差为0但双向各错（如银行多记100+企业多记100） | 分向列示+分向限额；加「笔数守恒」配合金额守恒 | 🟢可自补 |
| **关联方清单不全** ⚠️ | 场景特有 | 未标记的关联方交易根本不进检查，判据永远全绿 | 关联方识别引独立来源（工商股权 vs 财务系统标记交叉验证）；抵消分录禁用平衡科目兜底；未标记关联方、其余额或无法验证均计入 `all_ok`（已在脚本中实现） | 🟡需外部锚点 |

> **已接入** `scripts/intercompany_recon_v2.py`：对手方对称、类型一致、重复入账、单边配对提示、抵消差额分向列示与笔数守恒；关联方清单完备性直接内置于入口脚本（标记清单 ↔ 工商登记，并用全部客商余额量化未标记关联方）。
> **另附** `scripts/blindspot_anchors.py`（🟡半自动·检查+接源建议）：scope_completeness（关联方清单：财务标记↔工商股权登记双向交叉，抓漏登记的关联方；无第二源时诚实声明缺口）

### 可闭合性三档
- 🟢 **可自补**：加一段确定性检查即可闭合，零外部依赖——应直接实现。
- 🟡 **需外部锚点**：缺的是「第二个独立源」而非代码，须接入权威源（工商股权/银行/金税/合同）后方能校验——对客户标注为「需接入 X 源」。
- 🔴 **不可闭合**：结构上无验证基准（如员工自报项、需实物确认项），只能显式声明并交人工。

### 通用盲区补丁位（据本场景判据勾选）
- ☑ **范围完备性**：双向名单比对（A有B无 / B有A无 分别列示）——防「未进检查范围」的记录永远全绿
- ☑ **笔数守恒**：金额守恒之外加笔数守恒——抓成对反向错误
- ☑ **分向列示+分向限额**：正/负、双向单边分别设限——防净额掩盖
- ☐ **交叉白名单**：业务类型×允许值，白名单版本化+生效日——防「合法但不适用」
- ☐ **口径三元组**：时点+主体+准则声明 + 跨期衔接（本期期初=上期期末）——防口径错
- ☐ **归一化+模糊指纹**：去空格/全半角/前导零 + 组合键指纹——防唯一性绕过
- ☐ **外部锚点**：关键项引第三方独立源交叉验证——防同源错误
