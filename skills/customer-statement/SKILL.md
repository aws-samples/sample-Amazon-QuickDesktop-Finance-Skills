# 客户对账单生成

## Overview
为每个客户自动生成规范的往来对账单——列示期初应收、本期销售、本期收款、期末应收。核心验收判据是**恒等式 + 总量守恒**：逐户"期初+本期应收−本期收款=期末"成立，且各户合计守恒。本期期末结转下期期初，环环相扣，对账单可直接发送客户确认。

## 数据敏感性
往来数据含客户 PII。**执行前先加载 `financial-local-safety` skill**，本地模式处理。运行时模型只做编排、不接触原始交易数据，只看结果摘要；计算在本地沙箱由确定性脚本完成。

## 上层判据（不折旧 · 跨平台）
| 判据 | 规则 | 触发 |
|------|------|------|
| **恒等式** ⭐ | 期初 + 本期应收 − 本期收款 == 期末（逐户）| 不等 → 轧差错误 |
| **总量守恒** ⭐ | Σ期末 == Σ期初 + Σ应收 − Σ收款 | 不等 → 汇总错误 |
| **完整性** | 每笔流水归属唯一客户且计入 | 遗漏 → 明细缺失 |
| **符号一致** | 销售为正、收款为负（或分列） | 混淆 → 方向错误 |

- 可选：自讲解 HTML 仪表盘 / 逐户 PDF 对账单

## Lessons Learned
### Do
- 期初余额必须来自上期对账单的期末，环环相扣，形成月结链。
- 销售与收款分列两栏（本期应收、本期收款），比单一净额更清晰、易核对。
- 逐户恒等式 + 总量守恒两道 assert 都通过，对账单才可外发。

### Don't
- 不要发送未经恒等式校验的对账单。
- 不要混淆销售与收款方向——符号错误会导致期末余额反向。

### Common Failures
- 期初余额缺某客户：脚本仍为该户出对账单，期初按 0 列示并标待核实（「无期初余额记录」），由用户确认后从上期对账单补齐。
- 业务类型取值不统一（如"销售/开票/收入"混用）：先标准化映射再轧差。
- 中文表头 BOM：用 `encoding="utf-8-sig"`。

### When to Ask the User
- 期初余额来源（上期对账单 / 系统期初）、业务类型取值口径确认。
- 对账单是否需按企业抬头渲染成 PDF、是否自动发送客户确认。

## 判据
| 判据 | 规则 | 结果 |
|------|------|------|
| 跨期衔接 ⭐ | 本期期初 == 上期对账单期末（按客户编码 + 对账期间取紧邻上一期；其他期间的行不参与，同期多行 → 上期对账单重复）；上期未回签/有异议 → 待核实 | 不符 / 待核实 |
| 流水准入 ⭐ | 客户已登记；业务类型 ∈ 白名单；方向与类型一致；日期在本期；流水号唯一 | 不准入的剔除并逐笔列明 |
| 恒等式 | 期末 == 期初 + 销售 − 收款 − 退货 − 折让 | 自检 |
| 交叉一致 | 对账单期末 vs 明细账期末；差额 = 剔除流水影响 + 未解释差额 | 未解释差 → 不符 |
| 总量守恒 | Σ应收 == 1122 总账；Σ预收 == 2203 总账（借贷分列，不抵消） | 不符 |
| 数据质量 | 某户有行因数值无法解析被剔除（见 `data_issues`） | 含无法解析数据 → 至少待核实 |
| 范围完备 ⭐ | 期初余额、上期对账单、本期流水、明细账余额或因数值无法解析被剔除的行中任一出现过的户都出对账单，不丢户；无期初余额记录的户期初按 0 列示并标「无期初余额记录」，无明细账余额记录的户标「无明细账余额记录」 | 待核实 |

只有状态为“可发送”的对账单建议直接发给客户；`all_ok` 为 `False` 时先处理 `data_issues` 与问题标签，再决定是否外发。

- `samples/error/`：植入 13 处（期初≠上期期末、收款记正、退货登记成销售、跨期流水、流水重复、未登记客户、非白名单类型、上期有异议、明细账不符、总账未同步、5 月旧对账单冒充上期、上期对账单重复、发生额写成千分位无法解析且所属户判待核实），全部命中


## 自检 vs 正式运行（边界 · 必读）

本 skill 捆绑了 `samples/` 夹具与 `self_check.py`，**仅用于验证脚本本身是否健康，绝不参与正式业务运行**。两者必须严格分开：

| | 正式运行 | 自检（回归测试） |
|---|---|---|
| 输入 | **用户当期数据**，路径由调用者显式提供 | 内置 `samples/{clean,error}/` 夹具 |
| 入口 | `check(客户流水+台账目录)` | `python scripts/self_check.py` |
| 目的 | 核对这套业务数据 | 验证脚本行为与黄金答案一致 |
| 何时跑 | 每次业务核对 | 脚本改动后 / 定期体检 |

**铁律**：
- 校验函数**不设指向 samples 的默认路径**——数据路径必填，调用者给什么就核什么，绝不会在漏传时静默去核样本、假报"全部通过"。
- `samples/` 是隔离夹具（体检用），不是"默认数据集"，正式运行永不读它。
- 自检是独立命令（`self_check.py`），和业务运行不共用入口。

> **自检怎么用**：`python scripts/self_check.py` → 对 `samples/clean/` 应全部通过（全平），对 `samples/error/` 应低于 100% 并正好抓出植入的错误，与 `samples/expected.json` 黄金答案逐项比对；一致则退出码 0（脚本健康），不一致则非 0（脚本可能已退化）。植错版是最强验证器——有确定的已知错误数与期望值，脚本一旦退化立刻暴露。

## 判据覆盖声明与已知盲区

> 本场景判据可捕获：**守恒、恒等式、白名单、交叉一致、唯一性** 类错误。但每类自动校验都有其数学上的固有盲区——以下显式列出「判据抓不到什么」及对应处置。**「知道自己抓不到什么」比「能抓到什么」更是可信交付的证明。**

### 已知盲区（判据抓不到的错误类型）

| 盲区 | 关联判据 | 判据为何抓不到 | 处置 | 可闭合性 |
|------|:--:|------|------|:--:|
| 口径与时点 | 恒等式 | 等式内部自洽，但取数口径（时点/主体/准则）错，等式照样成立 | 口径三元组声明（时点+主体+准则）；跨期衔接校验（本期期初=上期期末） | 🟢可自补 |
| 净额掩盖 | 守恒 | 正负成对错误相互抵消，净差为0但双向各错（如银行多记100+企业多记100） | 分向列示+分向限额；加「笔数守恒」配合金额守恒 | 🟢可自补 |

> **已接入** `scripts/customer_statement_v2.py`：跨期衔接与上期回签状态、流水准入（客户/类型白名单/方向/期间/唯一）、退货与折让、对账单与明细账差额拆解、应收与预收分别对总账。

### 可闭合性三档
- 🟢 **可自补**：加一段确定性检查即可闭合，零外部依赖——应直接实现。
- 🟡 **需外部锚点**：缺的是「第二个独立源」而非代码，须接入权威源（工商股权/银行/金税/合同）后方能校验——对客户标注为「需接入 X 源」。
- 🔴 **不可闭合**：结构上无验证基准（如员工自报项、需实物确认项），只能显式声明并交人工。

### 通用盲区补丁位（据本场景判据勾选）
- ☑ **范围完备性**：双向名单比对（A有B无 / B有A无 分别列示）——防「未进检查范围」的记录永远全绿
- ☑ **笔数守恒**：金额守恒之外加笔数守恒——抓成对反向错误
- ☑ **分向列示+分向限额**：正/负、双向单边分别设限——防净额掩盖
- ☑ **交叉白名单**：业务类型×允许值，白名单版本化+生效日——防「合法但不适用」
- ☑ **口径三元组**：时点+主体+准则声明 + 跨期衔接（本期期初=上期期末）——防口径错
- ☐ **归一化+模糊指纹**：去空格/全半角/前导零 + 组合键指纹——防唯一性绕过
- ☐ **外部锚点**：关键项引第三方独立源交叉验证——防同源错误
